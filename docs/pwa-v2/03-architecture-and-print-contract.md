# Operational Plan PWA v2 — المعمارية وعقد الطباعة

## القرار المعماري الأساسي
يتم فصل التطبيق إلى ثلاثة أجزاء مستقلة منطقيًا:

1. **App Shell / UI** — الواجهة الحديثة متعددة المدارس.
2. **Data Layer** — IndexedDB ونموذج البيانات.
3. **Print Engine** — قالب الطباعة الرسمي المعتمد.

الهدف هو السماح بتطوير الواجهة والبيانات دون كسر الطباعة.

---

## 1) App Shell
مسؤول عن:
- Dashboard.
- التنقل.
- اختيار المدرسة.
- إدارة الخطط.
- إدارة التقويم.
- الإعدادات.
- النسخ الاحتياطي.

غير مسؤول عن:
- حساب مواضع عناصر الطباعة.
- تعديل أبعاد A4.
- تغيير CSS الخاص بالقالب الرسمي.

## 2) Data Layer
مسؤول عن:
- IndexedDB.
- CRUD للمدارس والخطط والأسابيع والأحداث.
- الهجرة من بيانات v1.
- النسخ الاحتياطي والاستعادة.
- المدرسة النشطة.
- التحقق من صحة العلاقات بين الكيانات.

## 3) Print Engine
يستقبل كائن بيانات جاهزًا من التطبيق ويعرضه داخل قالب الطباعة المعتمد.

### واجهة الإدخال المقترحة
```js
renderPrintTemplate({
  school,
  plan,
  weeks,
  events,
  staff,
  printProfile
});
```

### مبدأ مهم
Print Engine لا يقرأ IndexedDB مباشرة. واجهة التطبيق تجمع البيانات ثم تمرر Snapshot جاهزًا للطباعة. بذلك يصبح قالب الطباعة معزولًا وقابلًا للاختبار.

# عقد الطباعة Print Contract

## النسخة المعتمدة
اسم القالب الداخلي:

`print-template-v1`

مرجعه هو النسخة المستقرة الحالية في فرع `stable`.

## عناصر تعتبر ثابتة
لا يتم تغييرها أثناء تطوير PWA v2 إلا بطلب صريح واعتماد نسخة طباعة جديدة:
- A4 portrait.
- شبكة الأسابيع.
- ترتيب الصفحتين.
- شكل رأس الصفحة.
- مواضع الشعار وQR.
- طريقة عرض الإجازات داخل الأسابيع.
- شريط إجازة منتصف العام.
- هيكل التوقيعات.
- إصلاحات iPhone الخاصة بعدد صفحات الطباعة.
- قواعد الطباعة الخاصة بالكمبيوتر والجوال.

## عناصر مسموح بتغييرها من البيانات
- اسم المدرسة.
- المرحلة / نوع المدرسة.
- المنطقة والإدارة.
- الشعار.
- QR.
- العام الدراسي.
- الفترة.
- تواريخ الأسابيع.
- حالات الأيام.
- المناسبات والإجازات.
- أسماء المسؤولين ومسمياتهم.

## عناصر ممنوع كشفها كإعدادات للمستخدم
- zoom.
- scale.
- top / left / right / bottom بالـ mm.
- page height.
- CSS custom rules.
- media print overrides.
- break-before / break-after.
- transform.

هذه القيم تبقى تحت سيطرة المطور فقط.

# استراتيجية الاختبار قبل أي إصدار

## اختبار 1 — Desktop Print Regression
يجب مقارنة النتيجة مع `stable` والتأكد من:
- صفحتين فقط.
- عدم تغير شبكة الأسابيع.
- عدم انتقال التوقيعات.
- عدم ظهور تداخل.

## اختبار 2 — iPhone Print Regression
يجب التأكد من:
- صفحتين فقط.
- عدم ظهور صفحات بيضاء إضافية.
- عدم تداخل التوقيعات.
- المحافظة على التباعد المعتمد.

## اختبار 3 — Multi-School Isolation
- إنشاء مدرستين.
- تعديل خطة المدرسة الأولى.
- التأكد أن المدرسة الثانية لم تتأثر.

## اختبار 4 — Offline
- فتح التطبيق مرة واحدة متصلًا.
- قطع الإنترنت.
- إعادة فتح التطبيق.
- فتح مدرسة وخطة ومعاينة البيانات.

## اختبار 5 — Backup / Restore
- تصدير نسخة.
- حذف بيانات تجريبية.
- استعادة النسخة.
- مقارنة عدد المدارس والخطط والأسابيع والأحداث.

## ملاحظة تنفيذية
لن نفصل قالب الطباعة فعليًا في أول خطوة برمجية. أولًا نبني Data Layer وApp Shell، ثم نربط القالب الحالي بواسطة Adapter. بعد نجاح الاختبارات يمكن استخراج القالب إلى ملف مستقل دون تغيير الناتج.

# حدود الإصدار v2.0 الأول

## يدخل في v2.0
- مدارس متعددة على جهاز واحد.
- Dashboard جديد.
- معالج إنشاء مدرسة.
- خطط متعددة لكل مدرسة.
- تقويم وإجازات قابلة للإدارة.
- IndexedDB.
- نسخ احتياطي JSON.
- Offline PWA.
- نفس الطباعة المعتمدة.

## لا يدخل في v2.0 الأول
- حسابات مستخدمين عبر الإنترنت.
- مزامنة سحابية.
- صلاحيات مدير / وكيل عبر خادم.
- مشاركة خطة بين أجهزة متعددة لحظيًا.
- تغيير تصميم القالب الرسمي من واجهة الإعدادات.

هذه الميزات تؤجل إلى v2.1 أو v3 بعد ثبات الإصدار المحلي متعدد المدارس.
